# MOR Userbot Manager

این بسته، تمام منطق موجود در `MORSELF.py` را نگه می‌دارد و یک **پنل مدیریتی مالک‌محور در تلگرام** به آن اضافه می‌کند. پس از نصب، فقط شناسهٔ عددی مالک که در فرمان نصب تعیین می‌شود می‌تواند از ربات استفاده کند. پنل با `/start` باز می‌شود، ورود با شماره/کد/رمز دومرحله‌ای را انجام می‌دهد، session را با دسترسی محدود روی سرور نگه می‌دارد و یوزربات را در پس‌زمینه راه می‌اندازد.

> از توکن BotFather، کد ورود تلگرام و رمز دومرحله‌ای فقط در گفت‌وگوی خصوصی با ربات و روی سروری که به آن اعتماد دارید استفاده کنید. این ابزار از API حساب کاربری تلگرام استفاده می‌کند؛ رعایت قوانین تلگرام و مسئولیت استفاده از حساب بر عهدهٔ مالک حساب است.

## روش‌های اجرا

| رویکرد | مزیت و محدودیت | هزینه | دشواری راه‌اندازی |
|---|---|---:|---:|
| **همین بسته روی سرور لینوکسی با systemd** | مناسب درخواست فعلی: پایتون/Telethon، فایل session و اجرای دائمی را به‌طور مستقیم مدیریت می‌کند؛ پس از reboot خودکار بالا می‌آید. | هزینهٔ سرور فعلی | متوسط؛ یک فرمان نصب |
| اجرای محلی روی رایانه/Termux | بدون نیاز به سرور دائمی، اما برای پاسخ‌گویی و اتوماسیون باید دستگاه همیشه روشن و متصل بماند. | معمولاً رایگان | کم تا متوسط |

این بسته برای **گزینهٔ اول** آماده شده است، زیرا اسکریپت اصلی به Python/Telethon و فایل session دائمی نیاز دارد.

## قابلیت‌های حفظ‌شده و پنل جدید

| بخش پنل | عملیات |
|---|---|
| **مدیریت اصلی** | وضعیت، ورود/خروج اکانت، روشن/خاموش کردن یوزربات |
| **مدیریت سکوت** | افزودن/حذف/فهرست/پاک‌سازی چت‌ها و تنظیم دستورهای سکوت |
| **آرشیو پیام‌های PV** | پشتیبان محلی پیام‌ها، تشخیص حذف/ویرایش، نگهداری عکس/فایل/استیکر و جست‌وجوی چندروزه |
| **حذف پیام خواست** | حذف پیام Reply‌شده در همان PV با کلیدواژهٔ قابل تنظیم |
| **بررسی آنلاین** | بررسی یک کاربر با `@username` یا شناسهٔ عددی، با زمان انتظار قابل تنظیم |
| **ذخیرهٔ مدیا** | روشن/خاموش‌کردن ذخیرهٔ مدیای زمان‌دار، ورودی/خروجی و محافظت‌شده |
| **اتوماسیون** | Always Online، Auto Read، Auto Typing و کلیدواژه‌های آن‌ها |
| **هوش مصنوعی** | روشن/خاموش کلی، API Key، Base URL، مدل، شناسایی مدل‌ها و تنظیمات پاسخ |
| **حافظه و اطلاعات** | مشاهده و پاک‌سازی حافظهٔ چت‌ها، فهرست چت‌های AI، لاگ و تنظیمات امن |

منطق اصلی زیر در `MORSELF.py` باقی مانده است: سکوت و حذف پیام، ذخیرهٔ مدیاهای زمان‌دار و محافظت‌شده، تشخیص آنلاین، Always Online، سین، تایپینگ، پاسخ AI، حافظهٔ چت، استریم پاسخ AI، استیکرها و badAI. تنها دو اصلاح سازگار انجام شده است: کنترل کلی AI از پنل اعمال می‌شود و import موردنیاز برای مسیر انتظار بررسی آنلاین تکمیل شده است.

## نصب روی Ubuntu / Debian

### پیش‌نیازها

1. یک Bot از BotFather بسازید و **توکن** آن را داشته باشید.
2. شناسهٔ عددی تلگرام خودتان را داشته باشید. این همان `OWNER_NUMERIC_ID` است، نه username و نه شماره تلفن.
3. یک سرور Ubuntu/Debian با دسترسی `sudo` داشته باشید.

## دیپلوی روی Railway از GitHub

برای انجام مراحل ساخت پروژه، اتصال repository، ثبت Variables و ساخت Volume به‌صورت تعاملی، اسکریپت `deploy_to_railway.sh` نیز در پروژه قرار دارد. این اسکریپت از **Railway Account/API Token** استفاده می‌کند، نه Project Token؛ چون ساخت پروژه، سرویس و Volume عملیات سطح حساب هستند. Railway CLI باید قبل از اجرای آن نصب باشد:

```bash
bash <(curl -fsSL railway.com/install.sh)
chmod +x deploy_to_railway.sh
./deploy_to_railway.sh
```

اسکریپت به‌ترتیب توکن Railway، آدرس GitHub، branch، نام پروژه و سرویس، توکن BotFather و شناسهٔ عددی مالک را می‌پرسد. سپس Volume را با Mount Path `/data` می‌سازد و deployment را شروع می‌کند. توکن‌ها در فایل ذخیره نمی‌شوند و در خروجی چاپ نمی‌شوند. قبل از ساخت منابع، خلاصهٔ تنظیمات را نشان می‌دهد و تأیید می‌گیرد.

این پروژه برای Railway با یک `Dockerfile` آماده شده است و به‌عنوان یک **سرویس دائمی پس‌زمینه** اجرا می‌شود؛ بنابراین نیازی به بازکردن پورت عمومی یا اجرای `install.sh` داخل کانتینر نیست. Railway در صورت توقف پردازش، سرویس را طبق تنظیمات استقرار دوباره راه‌اندازی می‌کند.

### ۱. بارگذاری پروژه در GitHub

کل محتوای پروژه، از جمله `Dockerfile`، `requirements.txt`، `.dockerignore` و `.env.example` را در ریشهٔ یک repository قرار دهید و commit کنید. فایل `.env.example` فقط نمونه است؛ **توکن واقعی BotFather و شناسهٔ مالک را در GitHub قرار ندهید**.

### ۲. ساخت سرویس از مسیر GitHub

در [Railway New Project](https://railway.com/new/github)، حساب GitHub را متصل کنید، repository را انتخاب کنید و گزینهٔ **Deploy Now** را بزنید. Railway در ریشهٔ repository، `Dockerfile` با نام دقیق `Dockerfile` را پیدا و استفاده می‌کند. این رفتار در [راهنمای رسمی Dockerfile Railway](https://docs.railway.com/guides/dockerfiles) مستند شده است.

### ۳. افزودن Variables

در تب **Variables** سرویس این مقادیر را بسازید:

```text
MOR_BOT_TOKEN=توکن واقعی BotFather
MOR_OWNER_ID=شناسهٔ عددی واقعی تلگرام مالک
MOR_DATA_DIR=/data
```

`MOR_BOT_TOKEN` و `MOR_OWNER_ID` را به‌عنوان Secret نگه دارید و در صورت امکان پس از ثبت، آن‌ها را در Railway **Seal** کنید. تغییر یا افزودن Variables در Railway ابتدا به‌صورت staged change ثبت می‌شود و برای اثرگذاری باید Deploy انجام شود؛ این نکته در [مستندات Variables](https://docs.railway.com/variables) آمده است.

### ۴. ساخت Volume برای session و تنظیمات

از Project Canvas یا Command Palette گزینهٔ ساخت **Volume** را انتخاب و آن را به همین service متصل کنید. Mount Path را دقیقاً روی زیر تنظیم کنید:

```text
/data
```

این مسیر مهم است؛ session تلگرام، تنظیمات، فهرست چت‌های ساکت، آرشیو پیام‌ها و رسانه‌ها در آن نگهداری می‌شوند. Railway می‌گوید Volumeها برای داده‌های پایدار بین deploymentها هستند و مسیر نسبی `./data` باید در کانتینر به `/app/data` متصل شود؛ این پروژه برای جلوگیری از ابهام مستقیماً از `/data` استفاده می‌کند. جزئیات در [مستندات رسمی Volume](https://docs.railway.com/volumes) قرار دارد.

### ۵. ورود اولیه و اجرای خودکار

پس از Deploy، در تلگرام به ربات بروید و از همان حساب مالک `/start` بفرستید. از پنل ربات مسیر **ورود / خروج اکانت ← ورود اکانت** را انتخاب کنید و شماره، کد ورود و در صورت نیاز رمز دومرحله‌ای را بفرستید. این پروژه login را از طریق پنل ربات انجام می‌دهد؛ لازم نیست token یا آیدی را داخل Shell Railway به‌صورت دستی اجرا کنید. پس از موفقیت، فایل session داخل `/data` ذخیره می‌شود و در restart یا deployment بعدی از همان session استفاده خواهد شد.

### ۶. بررسی لاگ و عیب‌یابی

در تب **Deployments → View Logs** باید ابتدا اجرای manager bot را ببینید. اگر مقدار Variables اشتباه باشد، برنامه با پیام واضح دربارهٔ `MOR_BOT_TOKEN` یا `MOR_OWNER_ID` متوقف می‌شود. اگر پیام «No authorized session found» دیدید، طبیعی است و یعنی ورود اولیه هنوز از پنل ربات انجام نشده است. اگر بعد از ورود session باقی نماند، ابتدا Mount Path Volume را بررسی کنید؛ مقصد باید `/data` باشد.

نکات مهم Railway:

- این service یک worker است و به `PORT` یا Public Domain نیاز ندارد.
- `install.sh` برای Ubuntu/Debian معمولی است و در Railway نباید اجرا شود.
- برای حفظ session، فقط image کافی نیست؛ Volume ضروری است، چون فایل‌های داخل کانتینر بدون Volume پایدار تضمین نمی‌شوند.
- هر Push جدید به branch متصل‌شده می‌تواند deployment جدید بسازد؛ قبل از Push، Dockerfile و Variables را بررسی کنید.

### انتقال و نصب

پوشهٔ این پروژه را روی سرور منتقل کنید. سپس در همان پوشه اجرا کنید:

```bash
chmod +x install.sh
sudo ./install.sh 'BOTFATHER_TOKEN' 'OWNER_NUMERIC_ID'
```

نمونهٔ شکل فرمان (از مقادیر واقعی خودتان استفاده کنید):

```bash
sudo ./install.sh '123456789:AAExampleBotToken_xxxxxxxxx' '123456789'
```

نسخهٔ فعلی نصب‌کننده ابتدا بررسی می‌کند که Python و `venv` روی سیستم موجود باشد. اگر موجود باشند، **`apt-get update` را اجرا نمی‌کند**؛ بنابراین خرابی مخزن Kali باعث توقف نصب برنامه نمی‌شود. اگر Python/venv موجود نباشد، نصب‌کننده `apt-get update` را با محدودیت زمانی اجرا می‌کند و خطای مخزن را واضح نمایش می‌دهد، نه اینکه بی‌صدا متوقف بماند.

نصب‌کنندهٔ اصلاح‌شده دیگر `pip` را قبل از نصب برنامه ارتقا نمی‌دهد؛ این ارتقا ضروری نبود و در شبکه‌های دارای proxy یا اتصال ناپایدار می‌توانست با خطای `IncompleteRead` متوقف شود. نصب وابستگی‌های واقعی با timeout و retry انجام می‌شود.

اگر روی Kali خطای مخزن دیدید، قالب منبع رسمی باید شبیه این باشد:

```text
deb https://http.kali.org/kali kali-rolling main contrib non-free non-free-firmware
```

در WSL یا سرورهای مینیمال که `systemd` فعال نیست، نصب‌کننده از launcher پس‌زمینه استفاده می‌کند و مسیرهای start/stop/log را در پایان نصب چاپ می‌کند. در سرور معمولی که `systemd` فعال است، سرویس با reboot خودکار بالا می‌آید.

هنگام کپی‌کردن فرمان از راهنما، فقط خود فرمان را وارد کنید؛ علامت‌های محیط ترمینال مثل `┌──(root㉿...)` و `└─#` بخشی از فرمان نیستند و نباید کپی شوند.

نصب‌کننده به‌صورت خودکار:

- یک کاربر سیستم محدود به نام `morself` می‌سازد؛
- برنامه را در `/opt/morself-manager` نصب می‌کند؛
- token و شناسهٔ مالک را در `/etc/morself-manager.env` با مجوز محدود ذخیره می‌کند؛
- داده‌ها و session را در `/var/lib/morself-manager/data` با مجوز `0700` نگه می‌دارد؛
- سرویس `morself-manager` را فعال و اجرا می‌کند تا بعد از reboot نیز خودکار راه بیفتد.

### اولین ورود در ربات

1. در تلگرام، به ربات خود بروید و از **همان حسابی که `OWNER_NUMERIC_ID` آن را وارد کرده‌اید**، `/start` بزنید.
2. «**🔐 ورود / خروج اکانت**» و سپس «**➕ ورود اکانت**» را بزنید.
3. شماره را با کد کشور وارد کنید؛ نمونه: `+98912xxxxxxx`.
4. کد ورود را ارسال کنید. پیام‌های حاوی کد و رمز دومرحله‌ای پس از دریافت، تا حد امکان توسط ربات حذف می‌شوند.
5. اگر 2FA فعال باشد، رمز دومرحله‌ای را ارسال کنید.
6. پس از پیام «✅ ورود موفق»، session ذخیره و تمام سرویس‌های MORSELF خودکار روشن می‌شوند.

## مدیریت سرویس روی سرور

### مدیریت سکوت

در **قابلیت‌ها ← مدیریت سکوت ← مدیریت چت‌های ساکت**، همهٔ چت‌های ساکت به‌صورت متنی نمایش داده می‌شوند و کنار هر مورد نوع چت، مانند **پی‌وی** یا **گروه**، نوشته می‌شود. برای هر چت دکمهٔ **لغو سکوت** وجود دارد و از همان صفحه می‌توان چت جدید اضافه یا همهٔ موارد را پاک کرد. قابلیت سکوت اکنون برای گفت‌وگوی خصوصی، گروه و سوپرگروه کار می‌کند. در چت مقصد، کلیدواژهٔ فعال‌سازی پیش‌فرض `سوکوت` و کلیدواژهٔ لغو پیش‌فرض `لغو سکوت` است.

کلیدواژهٔ **حذف پیام** نیز در **تنظیم کلیدواژه‌های سکوت** قرار دارد و از همان‌جا قابل ویرایش است.

### آرشیو پیام‌های حذف‌شده و ویرایش‌شده

در بخش **قابلیت‌ها ← آرشیو پیام‌های حذف/ویرایش‌شده**، پیام‌های گفت‌وگوهای خصوصی در SQLite و رسانه‌ها در پوشهٔ `deleted_message_backup/media` نگهداری می‌شوند. گروه‌ها و کانال‌ها شامل این آرشیو نیستند. این قابلیت خودش درخواست `read` یا وضعیت آنلاین جداگانه ارسال نمی‌کند و در حالت پیش‌فرض «بدون سین» فعال است تا پیام‌های ورودی برای این قابلیت خوانده‌شده نشوند.

برای مشاهدهٔ موارد حذف یا ویرایش‌شده، گزینهٔ **بررسی آرشیو بر اساس تعداد روز** را بزنید و مثلاً `7` وارد کنید. مدت نگهداری پیش‌فرض ۳۰ روز است.

### حذف پیام خواست

در **مدیریت سکوت ← حذف پیام خواست** می‌توان قابلیت و کلیدواژه را تنظیم کرد. در همان PV روی پیام موردنظر Reply کنید و کلیدواژهٔ تنظیم‌شده را بفرستید؛ فقط پیام Reply‌شده در همان چت حذف می‌شود و در صورت فعال‌بودن گزینه، پیام دستور نیز پاک خواهد شد.

### حذف پیام

این قابلیت کاملاً مستقل از آرشیو پیام‌های حذف‌شده و ویرایش‌شده است و در **مدیریت سکوت ← تنظیم کلیدواژه‌های سکوت** قرار دارد. برای حذف پیام در گروه یا چت خصوصی، روی پیام هدف Reply کنید و کلیدواژهٔ پیش‌فرض **حذف پیام** را بفرستید؛ یوزربات همان پیام و دستور را حذف می‌کند. روش جایگزین این است که پیام موردنظر را برای ربات پنل Forward کنید؛ در این حالت ربات با استفاده از یوزربات پیام اصلی را از چت مبدأ حذف می‌کند. کلیدواژهٔ قدیمی **حذف پیام مشخص از چت** نیز برای سازگاری پذیرفته می‌شود.

برای **خاموش‌کردن کامل پنل و یوزربات** در سرور دارای systemd:

```bash
sudo systemctl stop morself-manager
```

برای خاموش‌کردن فقط یوزربات از داخل خود پنل، `/start` را بزنید و دکمهٔ **⏹ توقف یوزربات** را انتخاب کنید؛ در این حالت پنل باز می‌ماند و بعداً می‌توانید دوباره آن را روشن کنید.

```bash
# مشاهده وضعیت
sudo systemctl status morself-manager

# نمایش لاگ زنده
sudo journalctl -u morself-manager -f

# راه‌اندازی مجدد پس از به‌روزرسانی فایل‌ها
sudo systemctl restart morself-manager

# توقف یا شروع دستی
sudo systemctl stop morself-manager
sudo systemctl start morself-manager
```

اگر systemd فعال نباشد (معمولاً در WSL)، برای خاموش‌کردن کامل از این دستور استفاده کنید:

```bash
sudo /var/lib/morself-manager/stop-background.sh
```

نام پیش‌فرض فایل session اکانت کاربری اکنون `telegram_auto_delete_on_silence.session` است.

در راه‌اندازی مجدد، برنامه فایل Session موجود را با نام واقعی خودش شناسایی می‌کند؛ هم فایل‌های بدون پسوند مثل `telegram_auto_delete_on_silence` و هم فایل‌های دارای پسوند `.session` مثل `morself_userbot.session` پشتیبانی می‌شوند. فایل Session تغییرنام داده یا دوباره ساخته نمی‌شود. برای دیدن خطای واقعی شروع سرویس در systemd از `sudo journalctl -u morself-manager -n 100 --no-pager` استفاده کنید.

## به‌روزرسانی کد

فایل‌های جدید `MORSELF.py`، `manager_bot.py` و `requirements.txt` را جایگزین کنید، سپس همان فرمان نصب را دوباره اجرا کنید. تنظیمات و session در `/var/lib/morself-manager/data` هستند و با نصب مجدد پاک نمی‌شوند.

## نکات امنیتی

- Bot token، کد ورود و رمز 2FA را در کانال یا گروه ارسال نکنید.
- این نسخه فقط یک `OWNER_NUMERIC_ID` دارد و کنترل‌ها فقط در گفت‌وگوی خصوصی همان مالک کار می‌کنند؛ هر حساب یا گروه دیگر پیام «دسترسی ندارید» می‌گیرد.
- API Key هوش مصنوعی در فایل تنظیمات خصوصی ذخیره می‌شود و هرگز در «مشاهدهٔ تنظیمات امن» نمایش داده نمی‌شود.
- برای حذف کامل ورود حساب، از داخل پنل «خروج از اکانت» را بزنید؛ این کار فایل session را حذف می‌کند اما تنظیمات قابلیت‌ها را باقی می‌گذارد.
- تنظیمات پیشرفته اجازهٔ تغییر شماره، مسیرها یا نام session را نمی‌دهد تا داده‌های حساس به مسیر دلخواه منتقل نشوند.

## آزمون آفلاین

پس از نصب وابستگی‌ها می‌توانید این آزمون بدون اتصال به تلگرام را اجرا کنید:

```bash
/opt/morself-manager/.venv/bin/python /opt/morself-manager/test_manager.py
```
